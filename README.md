# 標籤條碼檢查

標籤稿在開印前要有人確認過才放行，這支程式就是那道關卡：
**把每個條碼解碼出來，跟條碼下方印的人眼可讀數字逐字比對。**

條碼與人眼可讀文字常常是分開產生的（兩者的資料來源不保證同一份），只要有一邊打錯就會不一致。這種錯誤是**逐批獨立發生**的，所以**每一批都要全數檢查，不能抽驗**——上一批乾淨不代表下一批乾淨。

> **另有純網頁版**：<https://pokaihsu1243-create.github.io/label-barcode-check/>
> 判定邏輯與門檻和這一版相同（實稿逐字比對過一致），但不必安裝任何東西、開網址就能用，
> 而且快 2～3 倍。原始碼在 <https://github.com/pokaihsu1243-create/label-barcode-check>。
> 這一版（桌面版）目前多的是：吃 TIFF 多頁掃描檔、以及可以自動產出一個 .pdf 報告檔。

## 怎麼用

有兩種入口，檢查邏輯完全一樣（都跑 `check_labels.py`）。

### A. 網頁版（有介面，建議用這個）

雙擊桌面「**標籤條碼檢查（網頁版）.bat**」→ 自動開 `http://localhost:8720`

- 把 PDF／照片**拖進頁面**（可一次多個），或點一下選檔
- **「應有條碼總數」要填**——不填就不做總數核對，也拿不到「可以放行」
- 也可以**貼上電腦上的檔案路徑**，這種方式報告會直接存在原檔旁邊
- 結果直接在頁面上看：大字結論、統計卡片、每列的條碼圖＋逐字比對＋判定依據
- 「複製異常清單」一鍵複製回報、「下載報告 HTML」存單一檔案

port 8720（其他工具用 8712／8714／8716／8718）。關掉黑色視窗就停止服務。

### B. 拖檔版（不開瀏覽器）

把標籤 PDF **拖到桌面「標籤條碼檢查.bat」上**（可一次拖多個），或雙擊選檔。
會先問「這份稿應有幾個條碼」——填了才做總數核對，直接按 Enter 就跳過（那就拿不到放行）。
跑完自動開啟報告 `<檔名>_條碼檢查報告.html`，存在來源檔同一個資料夾。

兩種都接受**照片／掃描檔**（jpg/png/tif），可用來抽驗實際印出來的標籤。

指令列用法（`--expect` 可指定應有條碼總數，做為數量核對的雙保險）：

```bash
python check_labels.py 檔案.pdf --expect 8
```

離開碼：0 = 全部一致且已核對數量；1 = 有異常或未能核對數量。

## 輸出 PDF

三種方式，都不需要另外裝東西（用 Windows 內建的 Edge 無視窗模式轉，全程離線）：

| 方式 | 怎麼做 |
|---|---|
| 網頁版 | 結果卡片右上角「**下載 PDF**」 |
| 報告本身 | 開啟報告 → 左上角「**🖨 列印 ／ 存成 PDF**」（或 Ctrl+P） |
| 指令列 | 加上 `--pdf`，會在報告旁邊多產生一份同名 .pdf |

列印版會自動**轉成 A4 橫式**（表格才塞得下 6 欄）、隱藏旋轉按鈕、保留顏色，
原圖對照頁會縮成剛好一頁。實測一份 8 個條碼的稿約 4 頁、1.2MB。

**踩過的坑：Edge 的命令列參數含非 ASCII 路徑會卡住不回應**（報告檔名有中文），
所以程式一律先複製到暫存區用純英文檔名轉，轉完再搬回原檔名。

## 判定等級

**OK 需兩次 OCR 均讀到相同文字，且完整模板辨識與 OCR 一致。** 字形群聚的票源仍是 OCR，不能單獨充當第二個獨立證據。PDF 文字層只作輔助，不能代替實際可見的印字。

| 判定 | 意思 |
|---|---|
| `OK` | 條碼與文字一致，兩次 OCR 與完整模板辨識相符，且沒有其他辨識衝突 |
| `NG` | 條碼與文字不一致 |
| `CHECK 需人工確認` | 第二次 OCR 缺讀或與第一次不同、模板辨識不完整、文字層與可見印字不同、各辨識軌有衝突、條碼傾斜。低信心 OCR 僅在完整模板同意時可下結論，並註明原因 |
| `讀不到文字` | 條碼下方抓不到文字 |
| `格式異常` | 條碼與文字一致，但料號不符 `9碼+A+8碼日期` |

報告的「依據」欄會寫清楚每一列**憑什麼**下這個判定。

## 檢查項目

| 項目 | 說明 |
|---|---|
| 條碼 vs 下方文字 | 主檢查，不一致的字在報告裡標紅 |
| 條碼方向 | 0°／90°／180°／270° 全部支援，文字區由條碼四角推算，四個方向共用同一套算式 |
| 條碼數量 | **只有你提供應有總數才算核對完成**（`--expect`／bat 提問／網頁欄位）。程式另會比較各標籤間的數量落差當「提示」，但那只是提示——每張標籤都漏讀同樣數量時，眾數會跟著一起錯，看不出來 |
| 同一張標籤多個條碼 | 內容必須相同 |
| 料號格式 | 預設 `9碼數字 + A + 8碼日期`，改 `check_labels.py` 的 `CODE_RE` |
| 傾斜 | 條碼傾斜超過 `MAX_SKEW`（預設 5°）不判讀，直接 CHECK |

## 原圖對照頁

報告最上面有一張**整頁原圖**：把條碼解出來的內容用紅字貼在**該標籤印刷數字的正下方**，
方向跟著標籤本身走（原稿顛倒的，補上去的也跟著顛倒），可以照原本的版面逐張核對。

- **綠框**＝與印的數字相符
- **紅框＋叉**＝條碼與印字不符（NG）
- **橘框＋問號**＝還沒確認（CHECK）——跟「不符」是兩回事，原因看下方表格的「依據」欄
- **紅字逐字對齊印刷字**——每個數字畫在它對應的印刷數字正下方，可以一欄一欄往下核，
  不用讀完整串再比。字級以字距為上限自動決定，所以不會擠在一起
- 小編號（1-2 之類）與不符的叉號放在**框外左側**，框內完全留給數字，不干擾對齊；
  編號對應下方表格的「頁-標籤」，方便交叉比對
- **可以左右轉 90°**（還有「回正」）——照實際貼標方向核對比較不會看錯；旋轉純顯示，不影響判定

位置是用**實際切出來的字**定位的，不是用文字區帶——用區帶會掉到下一張標籤上（踩過）。

## 疊合對照（給人眼的最後一道）

報告每一列都附一張疊合圖，三條帶：

| 帶 | 內容 |
|---|---|
| **條碼疊合** | 把**條碼解碼出來**的字（紅），逐字疊回原本印刷的字上 |
| **OCR疊合** | 把 OCR 讀到的字（藍）疊上去 |
| **三排對位** | 由上到下：原印字（黑）／條碼字（紅）／OCR字（藍），按字的位置對齊 |

**紅字和黑字對不上＝條碼與印字真的不一致。這條完全不依賴 OCR** ——
對位是用字形切割算的、紅字是解碼來的，兩者都不經過 OCR。

### 而且程式會自己看

疊合對不對得上**不是只靠你的眼睛**：程式把條碼說的那個字用字型渲染出來，
直接跟印刷字比**形狀相似度**（不是問「這是什麼字」，只問「這形狀像不像條碼說的那個字」），
36 個候選字元挑最像的一個。這條路完全不經過 OCR。

實測這份稿的 144 個字，**模板比對 top-1 全中（144/144）**，
最佳與次佳的相似度差距中位數 0.167、最小 0.056，邊界很清楚。

結果會寫在報告的「依據」欄：
- ⚠ 紅字：`疊合比對：第 2 個字與條碼對不上（第2字印的像 7、條碼是 2）`
- ✓ 綠字：`疊合比對：18 個字形狀全部吻合條碼（把握度 0.07）`

**它是第三條獨立軌，而且是唯一能抓到「OCR 兩軌一起錯」的檢查**（字形覆核的票源仍是 OCR，
所以 OCR 對某個字體系統性誤讀時，那兩軌會一起錯、一致、而且很有信心）。
只要模板比對的結論和文字判讀不同，該列就會升級成 CHECK，程式不會替你選一邊。

紅框＝模板比對判定與條碼不符的字（不經 OCR）；橘框＝程式自己也不確定的字。
對得準的時候紅字會完全蓋在黑字上（看起來就是一排乾淨的深紅字），錯位的那個字會明顯糊在一起。

## 原理與可靠度

- **條碼內容：解碼，不是 OCR。** zxing-cpp 解 Code 128，含 start/stop 圖樣與 mod-103 檢查碼。
  實測 720 次破壞（噪點＋隨機塗抹）**沒有一次吐出錯誤字串**，壞掉的結果是「掃不到」而不是「掃錯」。
- **下方文字：**
  1. PDF 文字層可能隱藏、過期或被覆蓋，只能作輔助；依頁面旋轉角度定位，並與可見印字比較。
  2. PDF 可見印字以 **400dpi 與 800dpi 各辨識一次**；圖片使用原圖及放大圖。兩次辨識都來自同一 OCR 模型，並非獨立來源。任一次缺讀、或兩次不同就不判 OK ——
     **不會**因為某一次剛好等於條碼就採用它（這種「重試到答案合意為止」的偏袒邏輯會往漏檢方向偏，已移除）。
  3. OCR 信心低於 `MIN_SCORE`（預設 0.80），只有完整模板辨識也讀出相同文字時才下結論，並註明信心偏低。
- **字形覆核（輔助手段，不是獨立辨識器）：** 把整份檔的字依形狀分群，同一形狀的所有實例用
  OCR 票多數決定它是哪個字。票源仍是 OCR，它獨立的是**錯誤模式**而不是資訊來源。
  票數 < 2、平手、或得票比例低於 `GLYPH_PURITY`（預設 0.80）→ 該字標 `?`，該列改判 CHECK。
  分群**先按字級分組**再比對：實測整份稿混在一起時「同字最低 0.876／異字最高 0.915」是重疊的，
  單一門檻分不開（`6` 和 `8` 會併在一起）；限定同一字級內則同字最低 0.926、異字最高 0.915，
  中間有空隙，門檻 `SIM_TH` 取 0.92。同一個字在不同字級各自成群沒關係——分開只是少共用票，
  併錯才會出事。污染超過一半時票會打平，那時輸出 `?` 說不知道，不硬猜。
- **字串比對：** 預設只忽略空白（空白是組字串時自己加的），**大小寫與標點不忽略**；
  要放寬請改 `IGNORE_CASE` / `IGNORE_PUNCT`，報告一律顯示原文。

## 驗收測試

測試會用到實際的標籤稿（含真實料號），所以**不放在這個專案裡**，改放在：

```
（與本專案同層的 label-barcode-check-tests 資料夾）
```

那裡有 `test_acceptance.py`（22 項：原稿結論、四種旋轉、低信心 OCR、兩次 OCR 衝突、
字形覆核失效、缺條碼、總數核對、辨識衝突、兩軌一起錯、模板重試的三種情況）、
`test_ocr_robustness.py`（3 項：竄改 OCR 模擬假警報／漏檢／少量污染）、
以及 `test_regressions.py`、`test_web_api.py`、`test_pdf_export.py`（20 項，使用自產測試檔）。

改動這支工具之後請回去跑一次，那是「OK 就是 OK」的唯一依據。

## 新增回歸測試

```powershell
python -X utf8 -m unittest -v test_regressions test_web_api
python -X utf8 -m unittest -v test_pdf_export
```

`test_regressions.py` 使用自行產生的測試檔，涵蓋第二次 OCR 缺讀、部分模板衝突、隱藏 PDF 文字、旋轉文字定位、多頁 TIFF、無效總數與 HTML 字元跳脫。
`test_web_api.py` 在暫存資料夾與獨立連接埠檢查路徑／上傳入口、錯誤總數、報告存檔和同時請求。API 測試使用固定辨識結果，真實 OCR 由既有驗收測試負責。

多頁 TIFF 現在逐頁檢查；圖片先套用 EXIF 方向。PDF 改為逐頁渲染，避免一次保留整份文件的高解析度影像。網頁的辨識請求依序執行，避免共用 OCR 模型與快取互相干擾。

同名檔案同時上傳使用不同暫存檔名，避免覆蓋。錯誤提示保留在畫面，重新下載 PDF 時會清除舊錯誤。
Edge 啟動程序可能先結束、PDF 稍後才由背景程序寫出；匯出現在會等待檔案大小穩定且可開啟，並在逾時或瀏覽器失敗時提供原因。

## 已知限制

- **總數核對只能靠你提供的數字。** 程式自己從辨識結果推出來的數量不能拿來驗證自己——
  每張標籤都漏讀同樣數量時，眾數會跟著一起錯（驗收案例 7 就是在證明這件事）。
  所以沒填應有總數時，即使逐張都一致也只會說「總數未核對」。
- 字形覆核需要同一字形在檔內出現 2 次以上；若票數不足但 OCR 與完整模板仍吻合，可以下結論。模板不完整時仍須看圖確認。
- 模板疊合比對**固定在 400dpi 與 800dpi 各跑一次**（不是「只在讀不出來時才重試」——那會變成只在
  對自己有利時才複查）。逐字合併：某一邊讀不出來就用另一邊補；**兩邊都讀出來卻讀成不同的字 → CHECK**，
  高解析度不能覆蓋已偵測到的衝突。重試一律重新比對全部 36 個候選字元，**絕不拿條碼的預期答案去找相似字**。
- 照片／掃描檔的「放大」是內插、沒有新資訊，所以**圖片輸入的高解析度結果不能拿來補字**，只能維持 CHECK。
- 模板目前使用 Arial 字形，陌生字型、模糊照片及字元黏連可能增加 CHECK。通過測試不代表所有字型或實際印刷品質均已驗證。

## 實測紀錄

首次實戰：某一批標籤稿 8 個條碼，抓到 4 個不一致——同一種尺寸的兩張標籤，條碼編出來的料號第 2 碼與印刷數字不同，而且同一張標籤上左右兩個條碼錯得一模一樣，屬於產生時打錯字，不是隨機亂碼；另一種尺寸的兩張則完全正確。
這也是為什麼要逐批全檢——條碼與文字分批產生，一批乾淨不代表下一批乾淨。
